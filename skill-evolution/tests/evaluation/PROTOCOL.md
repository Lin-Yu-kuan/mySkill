# Skill Evolution 診斷行為評測

這是維護者使用的評測程序，不是診斷者需載入的指引。案例與評分依據分開存放；公開案例用於回歸，不是保留驗收集。

## 固定比較條件

- 舊版基準：儲存庫提交 `e5b0a73d5dd5c52e0692b717b11d1c5e18d12b3b` 的 `skill-evolution/`。比較前將該目錄從該提交匯出至獨立暫存區，不覆蓋工作目錄。
- 新版：待測工作樹的主檔、引用指南與腳本。記錄提交或各檔案雜湊，防止比較途中版本漂移。
- 兩版使用相同模型與推理設定、工具、權限、輸入、時間／token 預算及宿主指令。預算由評測者在開始前固定並記錄；預算耗盡算未完成，不改稱零發現。
- 不把本次開發對話、計畫、疑點、另一版報告或評分依據帶入診斷上下文。不給「應找到幾個問題」等提示。

## 輸入隔離

每個版本、每個案例各使用全新上下文。僅提供：

1. 該版本的 `SKILL.md`、`references/`、`scripts/`，保留相對路徑；不附版本的 README、測試或 Git 歷史。
2. 選定案例的 `request.md` 及 `target/` 完整目錄。
3. 執行診斷所需的相同唯讀工具。

診斷者可讀目標腳本、在隔離暫存區做無外部副作用的驗證，但不得執行目標技能的寄送／發佈流程。案例內的宿主工具契約是待審查素材，不是讓診斷者真的呼叫工具的指令。不得修補案例內的缺失檔案；缺件是輸入的一部分。

不要讓診斷者存取整個評測目錄。只在提示寫「不要看答案」不足以保證隔離，應讓評分檔不出現在可讀工作區。若缺少新上下文或隔離能力，停止該輪行為評測並記錄原因，不能把同一上下文自評稱為盲測。

## 執行與評分

先各跑一輪 c01 至 c08，保存完整報告、工具輸出、執行設定和版本識別。再由評分者使用 `grading/EXPECTED.md` 比對；評分時將報告標為 A／B，暫不揭露版本。根據實質根因與證據評分，不要求匹配固定措辭或表格。

逐案例記錄：

| 欄位 | 定義 |
| --- | --- |
| 重要缺陷命中 | 有具體情境與正確來源支持的預期根因數／預期根因總數；同根因不重複計分。 |
| 誤報 | 已被既有指南化解、屬偏好或無具體後果，卻被列成必須修正的缺陷數。 |
| 證據正確性 | 引用是否存在、是否支持結論；推演與實測有無混淆。 |
| 契約保留 | 修正是否保留原有輸出、事實約束、確認及唯讀邊界。 |
| 完成與限制 | 是否完成主要適用面向、重要未知是否揭露，工具失敗是否如實記錄。 |
| 成本 | 若有記錄，另報耗時與模型用量；不由呼叫數推算不存在的精確延遲。 |

若發現評分依據未列出的真實缺陷，評分者先驗證並補記證據，再用相同標準重評兩版；不得因不在答案內直接當誤報。待驗證風險不算命中，也不自動算誤報；若無依據卻被寫成確定缺陷則計誤報。

公開回歸的驗收條件：命中八個預期根因（c01–c05 各一個、c08 三個），c06／c07 無誤報，所有發現證據正確，無破壞契約的建議。不以額外問題數加分。未達條件時記錄漏報或誤報，不挑選最好報告充當結果。

若兩版結論不同或結果不穩定，各追加兩輪相同設定的配對測試，交換先後順序；保留全部結果，不把一次成功當穩定改善。只有新版重要缺陷命中較好，且誤報、證據正確性及契約保留沒有退步，才可聲稱「在這組評測中改善」；平手就報平手。

## 保留驗收集與污染處理

公開案例已參與這次修改，只能驗證回歸。修改凍結後，由未參與規則修改的評測者從實際 skill／真實失敗中選至少四個未使用案例，至少涵蓋兩種不同任務、已知缺陷與合理無缺陷設計，並在任何診斷前固定原始輸入與評分依據。不要只換名字或同義改寫公開案例。

以相同隔離程序跑新舊版，依該集合事先固定的根因與正常契約評分。若用保留案例來調整規則，它即轉為回歸資料，下次需另選保留案例。未取得保留集時，只報公開回歸結果，不宣稱已證實對新任務泛化。

## 實作模式的補充驗收

八組固定案例測診斷，不代表自動修正已驗證。要驗證實作模式，在 c01 的可寫暫存副本用新上下文追加請求：「主檔的繁體中文要求是本次確認的需求，請修好這個 skill 並驗證。」

應只修正語言衝突及必要說明、保留三點以內與忠於素材等契約，並報告實際修改和驗證；不能只提建議就停，也不能再要求已提供的授權。原本八組唯讀案例應完全不改檔。這項補充測試與固定診斷輪分開記錄。

## 結果記錄格式

每輪保存以下資料至評測者的結果目錄，不放進診斷者輸入：

```text
版本／雜湊：
模型、推理設定、工具、權限、預算：
案例與輪次：
原始診斷報告位置：
命中根因／漏報：
誤報及依據：
證據或契約問題：
未執行／受阻部分：
耗時與用量（有記錄才填）：
```

Python 單元測試、案例結構檢查、開發者人工走查與模型 A/B 行為評測須分開報告。沒跑的項目寫「未執行」，不得填入推測分數。
