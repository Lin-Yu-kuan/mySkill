# Skill Evolution（第一版：既有 Skill 唯讀診斷）

你的任務是對目標 Skill 進行**高可信度、克制、不套用預設重構模板的唯讀診斷**。
在提出任何修改建議前，先閱讀 [診斷判準指南](references/diagnostic_rubric.md)。

---

## 核心原則（強制遵守）

1. **唯讀診斷即終點（Read-Only Diagnostic Endpoint）**
   - 當使用者請求診斷、評估或檢查某個 Skill 時，預設只執行**唯讀診斷**，嚴禁直接修改目標 Skill 的檔案。
   - 嚴禁未經實測就機械式畫出大型並行架構圖、精算假想 Token ROI 表、或自動生成多代理骨架。
   - 允許且鼓勵在確認設計合理時給出**「現有設計已足夠，無需修改」**的結論，或在交付 **1～2 條最小修正（Minimal Patch）** 後直接結束。

2. **強制沿引用鏈讀取完整上下文（Reference-Aware Traversal）**
   - 嚴禁只看 `SKILL.md` 表面的抽象形容詞（如「自然口語」、「適度吐槽」）就斷言「目標定義模糊」。
   - 必須先順著 `SKILL.md` 內的相對路徑連結，完整讀取所有被引用的指南（如 `references/*.md`）與腳本（`scripts/*`）。
   - 可用 `collect-context` 盤點第一層。`linked_references` 只列主檔直接連結的現存檔案，`unlinked_support_files` 可能包含次層指南或命令列、純文字提及的腳本。
     ```powershell
     # 可由當前技能的 scripts 目錄執行輔助盤點：
     python "<skill-evolution目錄>/scripts/skill_diagnostic_helper.py" collect-context "<目標_skill_目錄路徑>"
     ```
   - 若引用指南中已包含具體行為邊界（如「吐槽操作麻煩、不轉成對人攻擊」）與同素材的好壞對照範例，必須認定為**「已有可用判準」**；嚴禁盲目建議新增句長上限、emoji 密度等會削弱原設計彈性的機械規則。

3. **區分「缺少判準」與「已有判準，但實測仍失敗」**
   - **缺少判準（Missing Criteria）**：`SKILL.md` 與所有引用檔案中僅有抽象詞，既無負向邊界也無正反示例。
   - **已有判準，但實測偏移（Execution Drift）**：文件與指南已定義清楚，但模型面對未參與設計的新素材（Holdout Material）時仍會寫偏。此時應針對具體失敗情境提出最小補強，而非推翻原規則。

4. **辨識語意極性與同義改寫的事實核對（Polarity- & Entailment-Aware Fact Check）**
   - 評估或設計事實防線時，**嚴禁依賴單純的「關鍵詞差集比對」**：
     - 關鍵詞差集會**漏掉意思相反的句子**（例如素材寫「目前沒有免費方案」，輸出寫「目前提供免費方案」，兩邊都有「免費」而被放行）。
     - 關鍵詞差集會**誤擋同義合理改寫**（例如素材寫「完全不收費」，輸出寫「免費使用」，因素材無「免費」二字而被誤擋）。
   - 關鍵詞表僅能作為「提醒需要核對的敏感主張信號」。針對**價格/收費、公開/開源狀態、功能是否已上線、安全性承諾**等關鍵主張，必須要求指出支持該主張的當次素材原句，並核對：
     1. **肯定/否定極性（Polarity）**：有無「不、沒、無、尚未、並非」等否定反轉。
     2. **時間與實現狀態（Temporality/Modality）**：是「已上線/已公開」還是「規劃中/預計/考慮中」。
     3. **對象與範圍（Scope/Entity）**：是否把範例背景（如「家人考國考」）套用到無關的新題材。

   - `check-claims` 以子句初篩費用與公開狀態。只有 `verified` 會回傳 `passed: true`；`contradicted` 表示發現矛盾，`needs_review` 表示需回到當次素材複核。診斷者仍須查證規則未涵蓋的內容。

5. **嚴格的機制採用門檻（Adoption Thresholds）**
   - 依目標 Skill 的**實際任務與互動契約**判斷，不套用預設架構：
     - 若原 Skill 預設只在指定單一平台時產出一版（如 `social-post-voice`），**不要**建議預設拆成四平台並行。
     - 若原 Skill 設計有明確的「使用者確認點」（如 `universal-animator` 先確認素材包才渲染成片），任何平行化建議都**必須保留該確認點**，只處理已確認後的獨立子工作。

## 唯讀診斷標準步驟

1. **完整讀取**：從目標主檔開始，以各指南所在目錄解析次層引用，逐層補讀至沒有新引用；也要讀取命令列或純文字實際使用的腳本。診斷時引用含有判準或行為的檔案與行號。遇到缺件或無法讀取，列出引用位置、缺少的路徑與無法查證的判準，該項保留為「無法查證」。
2. **盤點既有保護與互動契約**：
   - 列出該 Skill 已具備的判準、正反範例、單/多輸出條件與人工確認點。
   - 明確說明哪些部分「現有設計已足夠，不應改動」（避免誤傷原設計）。
3. **定位具體缺口（若存在）**：
   - 檢查是否有純機械規則（如關鍵詞比對）會漏掉極性反轉（「沒有免費 → 提供免費」）或誤擋同義改寫（「不收費 → 免費」），或是否存在未覆蓋的高風險邊界。
4. **交付結構化診斷表並結束**：
   每項發現必須使用以下四欄格式呈現，交付後即完成任務：

| 原文位置 | 會受影響的使用情境 | 最小修正建議 | 驗收方式（含未見過素材之正反測例） |
| :--- | :--- | :--- | :--- |
| 標註具體檔案與行號連結 | 具體說明何種輸入素材與輸出會出錯 | 僅提出最小、不破壞原架構的修改（或註明「現有設計足夠」） | 列出具體測試素材與預期結果（先比任務完成率、事實正確與語氣偏好，再比成本） |

## 版本檢查與更新

以下操作的目標是本次載入的 `skill-evolution` 目錄。依使用者的動詞選擇範圍：

| 使用者要求 | 操作與完成條件 |
| --- | --- |
| 檢查最新版本 | 讀取 `update_url` 與本機 `SKILL.md`，只比對主檔位元組，回報「相同」或「有差異」。任一端無法讀取則回報「無法判定」及原因。此次檢查全程唯讀。 |
| 更新此技能 | 從 `update_url` 暫存主檔，確認是有效的 `skill-evolution` 主檔，再替換本機 `SKILL.md`。 |
| 完整更新套件 | 從 `repository` 取得同一份版本快照，先暫存並確認其中的 `skill-evolution/SKILL.md`、`references/` 與 `scripts/` 齊備，再更新主檔及這兩個目錄中的上游檔案。本機額外檔案保留。 |

更新前先確認每個目標路徑都在授權範圍內，保存將替換的內容。逐檔寫入後重讀並與暫存來源比對；如遇失敗，還原本次已寫入的檔案（含移除本次新增的檔案），回報失敗原因與還原結果。只有所有目標都核對成功才回報完成，並列出實際更新範圍。
