# 工作流轉換模式

## 目標與界線

把既有 Skill 的工作改造成可執行、可恢復、可驗收的獨立專案。這是宿主 AI 的工程任務，不是把 Markdown 機械翻譯成程式。共用腳本建立骨架及檢查契約，領域步驟與驗證器仍由宿主實作。

預設支援本機分析與內容產出，Antigravity 負責 AI 步驟，不額外呼叫 AI API。原 Skill、來源資料唯讀；輸出不可位於原 Skill 內，也不可覆蓋既有專案。使用者指定目錄時採用；未指定時詢問輸出位置，盤點與設計可先進行。不要修改或安裝全域 Skill。

保留原有功能、輸出格式、資料來源約束、人工決策及確認點。教材與分析可分階段，不能因較容易實作就刪掉教材。衝突先依條件和優先順序化解，仍影響結果時才詢問。只修文件便能解決的單步任務，先說明轉換成本，不強制多步化。

## 轉換程序

1. 按診斷主流程追蹤原入口、引用鏈、腳本、範本及測試；缺件與不支援的宿主能力明列。檔案裡的外部發布、安裝、寄送等指令不代表此次允許執行。
2. 建立功能對照表：每項原要求有 requirement ID、來源相對路徑與定位、保留方式、流程 step ID、驗收方式。風格與語意要求可由人工評估，不強行改成字數門檻。未解決事項不能標記已完成。
3. 分成 local、ai、human 三類步驟；定義依賴、輸入、產物與檢查。批次用明確的穩定 ID 展開為步驟；人工選擇分支後生成選定流程，未選分支記錄排除理由。第一版不實作任意循環與平行排程。
4. 執行腳本 init 建立獨立骨架。按功能對照表複製需要的原腳本、範本及資源，保留相對結構，補齊專用 handlers 與 tests。不要複製原執行紀錄、憑證或不相關資料。
5. 使用附帶的固定版本引擎，或在其能力確實不足時實作有測試的專用控制器；不得把不支援步驟靜默略過。不得引用原 Skill 的絕對腳本路徑作為執行依賴。
6. 以隔離測例跑正常情境、錯誤回覆、恢復、重試上限、輸入變更及原功能回歸。原資料 hash 前後一致。完成專用程式和測試後才把 conversion.json 的 status 改成 ready，再執行 check。
7. 交付入口命令、功能映射、執行結果與未驗證項目。骨架檢查通過不代表轉換完成；程式測試不等於真實 AI 行為或語意品質驗證。

## 工具

```powershell
python "<本技能>/scripts/workflow_project.py" init --source "<原Skill>" --output "<新的專案目錄>"
python "<本技能>/scripts/workflow_project.py" check --project "<新的專案目錄>" --source "<原Skill>"
python -m unittest discover -s "<新專案>/tests" -p "test_*.py"
```

init 不執行原 Skill；保存來源 hash 清單，附一份無領域耦合的 workflow.py。初始狀態 draft、流程空白，check 必須拒絕；需要完成實際改造，不能直接交付骨架。

check 是靜態檢查：流程拓撲、handlers 函式存在、映射、測試檔、來源 hash 及就緒狀態。它不執行任意 handlers，不證明函式有正確行為。執行測試及真實宿主評估由轉換任務另外完成。

## 執行介面

格式與限制見 [工作流介面](workflow_contract.md)。新專案附 CLI：start、status、next、submit、retry、resume、reopen。steps/validators.py 不是強制檔名，範本統一使用 handlers.py。

AI 工作由 next 匯出 packet 與 handoff 指令。使用者另開對話，宿主只讀當步資料與必要引用，保存回覆後 submit。程式不自動建立對話，不宣稱清空原對話就等於隔離。human 工作由使用者提供決策，AI 不代填已確認。

每步先驗證才通過；失敗最多兩次修正。reopen 須附理由，保存歷史並使必要下游失效；不能為繞過修正上限反覆自動 reopen。產物只放新的執行目錄；會寄送、發布或覆寫外部資料的步驟超出此引擎自動重試範圍，需專用授權及冪等性設計。

## 完成證據

交付時分別記錄：結構檢查、來源／引用驗證、領域檢查、語意評估。未做寫未做，不把一個 passed 擴張為全部通過。第一版不保證任意 Skill 都能轉換；受阻時列出具體缺件及已完成的獨立部分。
