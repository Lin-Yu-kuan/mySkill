# 既有 Skill 唯讀診斷判準指南 (Diagnostic Rubric)

本指南供 `skill-evolution` 在執行既有 Skill 唯讀診斷時參照，確保每條建議皆有憑據、克制且可驗收。

---

## 一、 如何避免「把已定義的風格誤報為模糊」

1. **先走完引用鏈再下結論**
   - 許多高品質 Skill 會保持主檔案 `SKILL.md` 精簡，而將具體語氣特徵、正反改寫範例放在 `references/`（例如 `social-post-voice` 將「適度吐槽」的具體判準與好壞對照放在 `references/voice-guide.md`）。
   - **禁止行為**：只掃描 `SKILL.md` 出現「自然」、「適度」、「適量」等詞，就建議加上「每句不超過 X 字」、「每段最多 Y 個 emoji」等死板門檻。這類硬性數字往往會破壞自然文風。

2. **區分兩種不同性質的問題**
   | 問題類型 | 判定標準 | 正確處置方式 |
   | :--- | :--- | :--- |
   | **A. 文件缺少判準**<br/>*(Missing Criteria)* | 走完 `SKILL.md` 與所有 `references/` 後，某項要求只有抽象形容詞，既無「什麼能做/不能做」的邊界，也沒有任何正反範例。 | 補充 1 組同素材的「符合 vs 不符合」對照範例，或補上明確的負向邊界（不做什么）。 |
   | **B. 已有判準，但實測仍失敗**<br/>*(Execution Drift)* | 指南中已有清楚定義與範例，但用未參與設計的新素材實測時，模型仍偶爾違反某條規則。 | 保留原判準，僅針對實測失敗的具體漏洞補強提示位置或核對步驟，不推翻原設計。 |
   | **C. 現有設計已足夠**<br/>*(Sufficient as-is)* | 已有具體邊界與正反範例，且在未見過的新素材上表現穩定。 | 明確在報告中標示「現有設計足夠，無需修改」。 |

---

## 二、 事實檢查的設計判準：為何不能只做「關鍵詞差集」

在需要「忠於當次素材事實」的 Skill（例如社群貼文撰寫、產品介紹、履歷或報告改寫）中，若使用「關鍵詞集合差集（素材沒出現該詞，輸出就不能出現）」作為事實檢查，會同時產生嚴重的**漏報（False Negative）**與**誤報（False Positive）**：

### 1. 必考驗收測例對照表

| 測試案例 | 當次輸入素材 | 待檢核輸出稿 | 單純關鍵詞差集結果 | 極性與語意核對結果（正確行為） |
| :--- | :--- | :--- | :--- | :--- |
| **案例 1：詞一樣、意思相反（極性反轉）** | `「這個工具目前沒有免費方案，採訂閱制。」` | `「這個工具目前提供免費方案，歡迎試用！」` | ❌ **錯誤放行**<br/>（兩邊皆含「免費」二字） | ✅ **精準攔截**<br/>素材為否定極性（`沒有` + `免費方案`），輸出翻轉為肯定極性（`提供` + `免費方案`），屬嚴重事實錯誤。 |
| **案例 2：詞不同、意思相同（同義改寫）** | `「這是我週末做的小工具，完全不收費。」` | `「這是我週末做的小工具，可以免費使用。」` | ❌ **錯誤攔截**<br/>（素材無「免費」二字） | ✅ **正確放行**<br/>素材的「完全不收費」與輸出的「免費使用」在費用主張上同屬零成本（Zero-Cost）肯定極性，語意完全相容。 |
| **案例 3：時態與實現狀態越界（規劃變已上線）** | `「預計下個月會把匯出 PDF 功能做好並開源。」` | `「已經支援匯出 PDF 功能，而且程式碼已經開源！」` | ❌ **錯誤放行**<br/>（兩邊皆含「匯出 PDF」、「開源」） | ✅ **精準攔截**<br/>素材為未來/未實現狀態（`預計下個月`），輸出改寫為已實現狀態（`已經支援`、`已經開源`）。 |

### 2. 推薦的事實核對最小修正寫法
- **保留詞表作為「提醒信號（Trigger Signals）」**：當輸出涉及**價格/費用（免費、收費、訂閱）、公開狀態（公開、開源、內測）、功能進度（已上線、支援、預計、規劃）、安全保證（沒毒、安全）或個人背景（家人、朋友）**時，觸發核對。
- **核對三要素**：要求每一條觸發的主張，都必須能指出當次素材中的支持句，並核對 **(1) 肯定/否定極性、(2) 已實現/未實現時間狀態、(3) 作用對象** 是否一致。

## 三、 演化機制的採用門檻（何時不該拆並行、何時不該加腳本）

| 演化機制 | 採用門檻（必須同時滿足才建議引入） | 禁止引入的情境（反例） |
| :--- | :--- | :--- |
| **多子單元異步並行** | 1. 常態輸入就是要求一次產出多個彼此獨立的大型產物；<br/>2. 實測單次串列生成確實出現嚴重延遲或跨產物互相污染；<br/>3. 各子任務之間沒有待使用者確認的中間點。 | - `social-post-voice`：預設只產當次指定平台，少數指定多平台時篇幅也很短，拆四個並行子代理反而增加調度開銷與事實不一致風險。<br/>- `universal-animator`：必須先由使用者確認「動畫素材包」才能進入渲染，不可跨越確認點直接並行生成最終成片。 |
| **前置/後置輔助腳本** | 1. 規則 100% 確定且不含語意歧義（如拔除殘留 HTML 標籤、檢查同一網址是否重複出現超過一次）；<br/>2. 實測模型常漏做該清理步驟。 | - 用腳本硬卡每句字數、逗號數量或 emoji 個數來判斷「口語化」。 |
| **快取與多模型調度** | 1. 同一工作流包含高頻重複的純函數子步驟；<br/>2. 已經先透過未見過素材（Holdout Set）實測證明輕量模型不會導致事實錯誤或文風退化。 | - 尚未驗證品質是否達標，就先為了省 Token 把核心寫作或推理降級給輕量模型。 |

---

## 四、 驗證「改完真的更好」的實測原則（Holdout Evaluation）

1. **測試集隔離**：用來驗收修改效果的素材，必須是**未參與規則設計的新素材（Holdout Set）**，不能只跑生成器自帶的範例。
2. **評估優先序**：
   - **第一優先：事實正確率與任務完成率**（特別檢查極性反轉、時態越界、無中生有）。
   - **第二優先：文風自然度與使用者偏好**（原版 vs 修改版盲測對比）。
   - **第三優先：耗時、模型呼叫次數與重試成本**（報告中必須明確分開「估算值」與「實測值」；例如快取命中只能證明少一次模型呼叫，不能宣稱真實延遲為零）。
