# 完整診斷判準指南

本指南將「檢查完整」與「修改克制」分開。完整是涵蓋相關行為並追查重要疑點；克制是只修有依據的問題，不是只找一兩項。

## 一、通用檢查面向

先讀主檔及行為相關引用，再按下表走查。將各面向記為已檢查、不適用或受阻；同一證據可支援多個面向，不必各寫一份報告。只在具體後果值得查證時深入，不把所有可能性都當需求。

| 面向 | 要追問的問題 | 能支持發現的情境或證據 |
| --- | --- | --- |
| 觸發條件 | 描述是否讓正確請求選到此技能？是否吸引它不處理的工作？ | 描述承諾生成文件，正文卻只審查文件；用一則實際請求說明錯誤路由。 |
| 任務與完成標準 | 輸入足夠時能否產生要求的輸出？何時算完成？ | 要求可下載成品，流程卻在產生草稿文字後結束；完成條件與交付不同。 |
| 指令一致性 | 相同條件下是否要求互斥行為？是否已有明確優先順序？ | 主檔要求英文、適用指南要求繁中，且無可解決衝突的優先規則。 |
| 引用與依賴 | 次層引用、腳本、資產與工具是否存在且可取得？ | 引用檔缺失或命令需要未提供的輸入；記錄來源、解析後路徑與受影響步驟。 |
| 工具實際能力 | 文件承諾是否超過實作？輸出狀態是否被誤讀？ | 文件稱遞迴掃描，程式卻只列第一層；用巢狀輸入確認落差，不能只看函式名稱。 |
| 流程分支與失敗恢復 | 合理輸入、缺輸入、工具失敗時能否到達合法終點？ | 重試無停止條件、半成品被回報成功，或覆寫失敗後無法恢復已動過的資料。唯讀工作不強加回滾。 |
| 授權與確認點 | 動作是否符合當次要求與原有契約？ | 只要求預覽卻發佈、並行工作越過素材確認點，或已授權修改仍無條件要求再次批准。 |
| 驗收有效性 | 驗證是否檢查真正承諾的行為？有沒有反例與正常案例？ | 只測字串或固定示例就宣稱任務正確；評測答案洩漏給受測者。 |

對大型技能，可先盤點分支再按失敗影響分配深度；不可把未讀的相關分支記成已檢查。使用宿主適用的指令優先順序，避免將有明確適用條件的規則誤報為矛盾。工具或外部 API 行為不確定時，查可用的當前實作、官方文件或做受控驗證，不能靠記憶補成事實。

## 二、從疑點到可交付發現

對重要疑點依序完成以下核對；不用展開所有探索過程，只保留足以重現的依據。

1. **定位承諾與來源**：指出規則、腳本或依賴的檔案與行號，說明適用條件。多檔衝突需同時引用兩側。
2. **建立最小觸發情境**：給合理輸入與期望結果，沿指令或程式走到會卡住、違約或失真的位置；區分確定結果與模型可能的行為。
3. **主動找反證**：查次層指南、範例、例外、前置檢查及後置驗證。若既有規則已處理，撤回疑點；若只有部分處理，限縮範圍。不能用「模型可能忽略任何規則」指控每份 skill。
4. **判定證據層級與影響**：用下表標記，再以觸發條件及後果排序。越權、資料損失、核心任務失敗優先於偶發不便或表述改善；未知觸發頻率不虛構成高頻。
5. **合併根因並選擇修正**：同一根因造成多個症狀時合併，保留代表情境；不同原因不能為了縮短報告而合併掉。以修完後能否消除失敗路徑判斷充分性，而非以修改行數評分。

| 證據層級 | 成立條件 | 報告用法 |
| --- | --- | --- |
| 文件可證實的缺陷 | 靜態來源足以證明矛盾、缺件或實作與承諾落差。 | 引用原文／程式及觸發條件；不必先觀察模型失敗，但不能宣稱已跑過情境。 |
| 實際執行失敗 | 保存了輸入、版本、環境、實際輸出及與預期的差異。 | 附重現命令或測例與結果；把執行環境缺件和目標本身缺陷分開。 |
| 待驗證風險 | 有合理疑點，但缺少來源、外部能力確認或必要執行結果。 | 與已證實發現分開，寫清缺少什麼、如何查證；不直接要求按假設改寫。 |

「已有判準」與證據層級是兩件事。判準可能不完整、互相衝突或無法落實；但不能僅因它沒有採用自己偏好的措辭而判為缺陷。沒有發現時可結束，結論只涵蓋本次可取得的證據。

## 三、修正與交付

- **缺少必要判準**：先指出哪個合理決策無法由現有指引決定，再補最少的決策依據或正反例；抽象詞本身不是缺陷。
- **已有判準但實測偏移**：保留有效規則，針對實際失敗補提示位置、適用條件或驗證，不憑一次偏移推翻設計。
- **規則或實作互相衝突**：消除真正衝突的來源及其重複說明，不能再加一句同樣衝突的提醒。
- **結構性問題**：若局部修改仍留有同一失敗路徑，可調整流程或資料責任；說明必要性、受影響介面與原契約如何保留。不得預設改成多代理、快取或多模型架構，也不編造 Token ROI。

每項發現包含「影響與證據層級、位置、觸發情境、根因、修正、驗收」即可，不固定欄數。重要未知另列。診斷模式交付建議與測試設計；實作模式需交付實際改動與執行結果，不能在診斷表後提前停止。

驗收應針對修正的行為與保留的契約：選觸發原缺陷的案例、一個應繼續成功的相鄰正常案例，必要時加失敗恢復或授權案例。靜態矛盾可先由重讀相關文件驗收；模型品質結論需要行為評測。不要只測新文字存在，也不要把構想測例寫成通過。

## 四、任務特定檢查（僅在相關時使用）

### 文風與自然語言判準

讀完語氣指南與正反範例再判斷。例如已有「吐槽操作麻煩、不轉成人身攻擊」和同素材對照，就不能因主檔寫「適度吐槽」而主張沒有判準。句長、emoji 數量等機械門檻只有在任務本身要求時才採用。

若懷疑範例覆蓋不足，提供新的合理題材或互動情境，檢查同一判準能否適用；已有範例不代表所有情境已驗證。文風偏好需要使用者選擇或盲測，不能假扮成客觀錯誤。

### 忠於素材的事實核對

價格、公開／開源狀態、功能進度、安全承諾或個人背景等主張，應能回指**當次素材**支持句。敏感詞只提示要核對，不能用關鍵詞差集證明真假。

| 情境 | 素材 → 輸出 | 核對重點 |
| --- | --- | --- |
| 極性反轉 | 「沒有免費方案」→「提供免費方案」 | 否定變肯定，即使詞相同仍矛盾。 |
| 合理同義改寫 | 「完全不收費」→「免費使用」 | 相同對象與條件下可成立，不能因詞不同誤擋。 |
| 時間／實現狀態越界 | 「預計下個月開源」→「已經開源」 | 計畫不等於已實現；功能支援同理。 |
| 對象或範圍越界 | 「下載免費，匯出需付費」→「所有功能免費」 | 核對產品、版本、功能與限定條件；不要挪用範例個人背景。 |

`check-claims` 是有限句式的費用與公開狀態初篩，不是通用語意判定器。只有 `status: verified` 才回傳 `passed: true`；`contradicted` 表示至少有一項已辨識主張矛盾，`needs_review` 表示證據不足、對象不明或句式超出支援範圍。核對 `verified_alignments` 的輸出主張與素材支持句；混合結果仍需逐項複核，其他主張也由診斷者查證。不得將它通過當作整份 skill、文章或所有事實正確的證明。

### 多產物、工具及流程優化

- 單平台單產物任務不因存在多個平台就預設拆成四路。只在輸入確實包含獨立工作且有品質或耗時證據支持時評估並行，保留必需確認點。
- 決定性腳本適合可靠的結構處理；語意初篩則需明確的能力範圍與「無法判定」出口，不能把啟發式當成完整驗證。
- 快取或模型調度先證明不破壞正確性與契約，再比較成本；估算與實測分開，少一次呼叫不能推論延遲為零。

## 五、驗證診斷方法本身

本技能的維護評測位於套件根目錄的 `tests/evaluation/PROTOCOL.md`；它不是一般診斷時需讀的目標參考檔。評測者應按協議只交付選定案例及待測 skill，避免載入評分依據。

新舊版用相同模型、工具、輸入、權限與預算，在分離上下文中評測。比較重要缺陷命中、誤報、證據可追溯性，以及原有輸出／確認契約的保留；不以報告長度或問題總數打分。若有隨機性或差異不穩定，重跑配對案例並報告差異，不只挑最好的一輪。

參與規則設計的例子及公開評測案例都是回歸資料。真正的保留驗收集須未參與修改、未把預期答案提供給診斷者，並在評測前固定。不能宣稱新生成的同義改寫就是獨立驗收。沒有合適執行環境或保留案例時，明列未完成驗證，不宣稱診斷能力已提升。
